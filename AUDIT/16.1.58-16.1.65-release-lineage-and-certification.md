## Required production-certification gates

Do these in a backed-up disposable WordPress/MariaDB staging clone first, using synthetic records only. No diagnostic step should make live production postings or edit real data.

1. **Package and environment identity:** record the exact installer ZIP SHA-256; confirm the site plugin bytes/version, WordPress/PHP/MariaDB versions and available XLSX/file extensions; prove fresh install and in-place update behavior for the actual installed baseline.
2. **Physical schema and safe upgrade:** verify the 49/49 expected tables, primary keys, required accounting/HR columns and indexes, schema markers Core `16.1.1`, Accounting `16.1.15`, HR `16.1.3`; inspect upgrade logs for warnings/errors; verify setup-mode fail-closed behavior if a required schema item is absent.
3. **Deep read-only integrity:** run the actual `RUN DEEP INTEGRITY AUDIT`; capture every PASS/FAIL/UNKNOWN and the counts for orphan references, requisitions, audit chain, identifiers, stock/negative stock, reservations, PLEDGER, AP/AR, GL and payroll. An UNKNOWN or deferred check is not a PASS. Review foreign-key/relationship coverage on the clone; don't add constraints before orphan review and rollback planning.
4. **Owner/Management/Warehouse separation:** prove Management submission → active Owner approval/rejection → Warehouse Manager accepted partial/full receipt; self-approval and Management approval must be denied; test retry/idempotency and verify audit trail, on-hand quantities, PO balances, PLEDGER, GRNI, AP and GL reconcile.
5. **Operational inventory and POS:** test product/SKU search including focus/touch, selection and empty results; create/save a product and prove success/error notifications; prove Product Master catalog import never creates stock or sales; prove per-branch manual Daily POS Excel upload has scope, duplicate/replay protection and correct ledger/report attribution, and does not require an external POS API.
6. **Finance/payroll:** verify supplier invoices and payments remain separately Owner-approved as required, GL journals balance, HR schema setup is safe, taxable/exempt classification gates work, statutory PAYE effective-date treatment and pension arithmetic pass, and RETAINER_SERVICE records do not enter employee statutory payroll without approved handling.
7. **Responsive authenticated browser/host:** use actual authenticated Owner, Management, Warehouse and Branch roles. Record responsive behavior at 375, 576, 768, 900, 991, 992, 1024, 1280 and 1440 CSS px; verify SKU/POS/import/approval flows, cache refresh/PWA, upload permissions and PHP fatal/error logs on the real host.
8. **Recovery:** take file + DB backup, restore the backup to a clean disposable site, verify counts and ledger balances, execute rollback/reinstall rehearsal, and attach outputs.
9. **Evidence format:** for every check record a test ID, timestamp, environment, installed package SHA-256, role, steps, expected result, observed result, logs/screenshots and PASS/FAIL/BLOCKED. A gate is PASS only when the result is observed on the target environment.

## Final release decision rule

A passed repository source gate establishes source/package quality for its exact commit; it does not establish that the live ERP is safe or working. Final production certification is issued only after the complete target-host matrix above is PASS on the exact install package, the 49-table/schema/integrity/ledger results are clean, and backup/restore/rollback evidence is attached. If access to a controlled authenticated staging environment is unavailable, status remains **source-gate PASS / production certification pending evidence**; no false certification is issued.
